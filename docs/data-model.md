# ACME Compensation Hub — Data Model

**Version:** 1.0 · **Date:** September 26, 2026

---

## Overview

Two tables. `employees` holds identity and organizational metadata. `compensation_history` holds an immutable record of every salary change. All schema changes are managed through Liquibase changelogs — no manual DDL.

## Table: `employees`

```sql
CREATE TABLE employees (
    id          UUID         PRIMARY KEY DEFAULT gen_random_uuid(),
    full_name   VARCHAR(255) NOT NULL,
    email       VARCHAR(255) NOT NULL,
    department  VARCHAR(100) NOT NULL,
    job_title   VARCHAR(100) NOT NULL,
    country     VARCHAR(100) NOT NULL,
    status      VARCHAR(20)  NOT NULL DEFAULT 'active'
                             CHECK (status IN ('active', 'inactive')),
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),

    CONSTRAINT uq_employees_email UNIQUE (email)
);
```

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Generated by the database. Never exposed as a sequential integer to avoid enumeration. |
| `full_name` | VARCHAR(255) | Display name. Not split into first/last — the domain does not require it. |
| `email` | VARCHAR(255) | Unique. Used as a natural key for deduplication. |
| `department` | VARCHAR(100) | Free text, normalized to title case on write. |
| `job_title` | VARCHAR(100) | Free text. |
| `country` | VARCHAR(100) | Free text. ISO 3166-1 alpha-2 code recommended but not enforced at DB level. |
| `status` | VARCHAR(20) | `active` or `inactive`. Controlled by a CHECK constraint. |
| `created_at` | TIMESTAMPTZ | Set by the database on insert. |
| `updated_at` | TIMESTAMPTZ | Updated by the application on every write. |

**Indexes**

```sql
CREATE INDEX idx_employees_department ON employees (department);
CREATE INDEX idx_employees_country    ON employees (country);
CREATE INDEX idx_employees_status     ON employees (status);
```

These three indexes support the most common filter combinations on the employee list endpoint.

## Table: `compensation_history`

```sql
CREATE TABLE compensation_history (
    id             UUID          PRIMARY KEY DEFAULT gen_random_uuid(),
    employee_id    UUID          NOT NULL
                                 REFERENCES employees (id) ON DELETE RESTRICT,
    amount         NUMERIC(15,2) NOT NULL CHECK (amount >= 0),
    currency       CHAR(3)       NOT NULL,
    effective_date DATE          NOT NULL,
    changed_by     VARCHAR(255)  NOT NULL,
    created_at     TIMESTAMPTZ   NOT NULL DEFAULT now(),

    CONSTRAINT uq_compensation_employee_date
        UNIQUE (employee_id, effective_date)
);
```

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Generated by the database. |
| `employee_id` | UUID | Foreign key to `employees.id`. `ON DELETE RESTRICT` — an employee cannot be deleted while compensation records exist. |
| `amount` | NUMERIC(15,2) | Two decimal places. Maximum 13 digits before the decimal — sufficient for any realistic salary. Negative values rejected by CHECK constraint. |
| `currency` | CHAR(3) | ISO 4217 three-letter code (e.g., `USD`, `GBP`, `INR`). Stored in uppercase; validation enforced at the API layer. |
| `effective_date` | DATE | The date from which this salary applies. Set by the HR Manager, not auto-assigned. |
| `changed_by` | VARCHAR(255) | The identity of the HR Manager who made the change. Recorded for audit purposes. |
| `created_at` | TIMESTAMPTZ | The timestamp the row was inserted. Distinct from `effective_date`. |

**Indexes**

```sql
CREATE INDEX idx_comp_employee_date
    ON compensation_history (employee_id, effective_date DESC);
```

This index makes the "current salary" query fast — it is the hottest read path in the system.

## Deriving Current Salary

There is no `current_salary` column on `employees`. Current salary is always derived at query time:

```sql
SELECT DISTINCT ON (employee_id)
    employee_id,
    amount,
    currency,
    effective_date
FROM compensation_history
WHERE effective_date <= CURRENT_DATE
ORDER BY employee_id, effective_date DESC;
```

This query is fast because of the `(employee_id, effective_date DESC)` index. The application never caches or duplicates this value — the database is always the source of truth.

For a single employee:

```sql
SELECT amount, currency, effective_date
FROM compensation_history
WHERE employee_id = :employeeId
  AND effective_date <= CURRENT_DATE
ORDER BY effective_date DESC
LIMIT 1;
```

## Analytics Queries

Median salary requires a PostgreSQL window function. This cannot be expressed in JPQL and is written as native SQL:

```sql
SELECT
    e.department,
    COUNT(*)                                              AS headcount,
    ROUND(AVG(c.amount), 2)                               AS avg_salary,
    ROUND(PERCENTILE_CONT(0.5) WITHIN GROUP
          (ORDER BY c.amount)::NUMERIC, 2)                AS median_salary,
    MIN(c.amount)                                         AS min_salary,
    MAX(c.amount)                                         AS max_salary
FROM employees e
JOIN (
    -- current salary per employee
    SELECT DISTINCT ON (employee_id)
        employee_id, amount, currency
    FROM compensation_history
    WHERE effective_date <= CURRENT_DATE
    ORDER BY employee_id, effective_date DESC
) c ON c.employee_id = e.id
WHERE e.status = 'active'
  AND (:department IS NULL OR e.department = :department)
  AND (:country    IS NULL OR e.country    = :country)
GROUP BY e.department
ORDER BY e.department;
```

## Liquibase Changelog Structure

```
src/main/resources/db/changelog/
├── db.changelog-master.xml          ← includes all changesets in order
├── 0001-create-employees.xml
├── 0002-create-compensation-history.xml
├── 0003-create-indexes.xml
└── 0004-seed-data.xml               ← contexts="local,test" only
```

Each changelog file contains one logical change. The master file includes them in sequence. Liquibase tracks applied changesets in its `databasechangelog` table and will not re-run a changeset that has already been applied.

The seed changeset is gated with `contexts="local,test"` and will not run in a `prod` profile. It generates 10,000 employees with realistic distributions across departments, countries, and salary bands using a fixed random seed to ensure deterministic test assertions.

## Constraints Summary

| Constraint | Enforced at |
|---|---|
| Email uniqueness | DB (`UNIQUE`) + API validation |
| Employee status values | DB (`CHECK`) |
| Salary non-negative | DB (`CHECK`) |
| One salary record per employee per date | DB (`UNIQUE`) |
| Currency uppercase format | API layer (normalized on write) |
| Employee cannot be deleted with history | DB (`ON DELETE RESTRICT`) |
